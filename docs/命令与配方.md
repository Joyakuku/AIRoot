# 命令与维护配方

接口版本为 1。所有命令均支持全局 `--json`；查询返回实际状态，长任务返回 ID。文本模式可读；程序调用应解析 JSON。`--data-root` 是测试隔离入口，不是生产数据分散存放方案。

## 维护输入

`operation plan --file plan.json` 接受以下可选字段；配方会检查必需项：

| 字段 | 用途 |
|---|---|
| action | create / install-packages / upgrade-packages / remove-packages / delete / install-portable / bootstrap / import-wsl / pull-image / create-container / start / stop |
| resource_id | 修改对象；create-container 时为已登记镜像 ID |
| kind | venv、conda、python、node、java、cli 等 |
| name、project | 新实例名称和对应项目；环境要求两者 |
| target | 指定正常资源根目录下的新目标，或平台删除的迁出目录 |
| manager | 已存在的绝对解释器或管理器路径 |
| version | 请求版本；实际版本核实不匹配时保留安装供检查 |
| packages | 依赖列表；create-container 时为容器内命令及独立参数，不经宿主 shell |
| source | 公共 HTTPS 安装来源；pull-image 使用 repository@sha256:digest |
| archive、sha256 | 安装包或备份文件与哈希；远程下载可省略 archive，但不能省略 SHA256 |

方案包含 `risk`、`requirements`、`effects`、具体进程及参数、目标、项目和对象指纹。apply 前重新核实对象、管理器哈希、目标和使用保护；变更返回 PLAN_CHANGED。

```powershell
airoot operation apply <ID> --confirm source-reviewed --confirm compatibility-reviewed --confirm external-use-reviewed
```

这些条件由 Agent 按真实对话和权限管理履行。Full Access 信息不传给 AIRoot。删除必须带 `delete:<ID>`；删除依赖带 `remove-packages:<ID>`；容器停止/启动带 `stop:<ID>` / `start:<ID>`。不同配方以实际返回 requirements 为准，不应盲目填入所有字符串。

## conda 依赖维护

创建和依赖维护可指定 `source` 为已审核的 HTTPS channel，例如 `https://conda.anaconda.org/conda-forge`。命令使用 `--override-channels --channel`，不改全局配置；未提供时，方案明确要求审查既有 channel 配置。无版本约束的 `upgrade-packages` 使用 `conda update`，带版本约束使用 `conda install`。完成后读取该 prefix 的 conda-meta，刷新登记中的真实依赖。

## ZIP 安装

```json
{
  "action": "install-portable",
  "kind": "cli",
  "name": "fd",
  "project": "file-search",
  "source": "https://github.com/sharkdp/fd/releases/download/v10.5.0/fd-v10.5.0-x86_64-pc-windows-msvc.zip",
  "sha256": "a227701b8551c35a9931d9f6da75503cf86d88e182d71fb849a70864c5d57cd7"
}
```

下载由固定 curl 参数完成，仅 HTTPS/HTTPS 重定向，连接和总时限有界，瞬时下载失败最多重试两次。包管理器修改不做盲目自动重试。先核对整个压缩包成员，再写入新目标；禁止路径穿越、ADS、Windows 保留名称、大小写冲突和链接。

## 基础安装

bootstrap 只支持官方 Python x64 EXE 和 conda-forge Miniforge Windows x64 EXE。必须提供具体版本来源与固定 SHA256、名称和项目。Python 使用固定每用户无 PATH/关联/启动器配方；Miniforge 使用固定 JustMe、不注册默认 Python 的配方。供应商安装器维护其正常安装记录，不能假定全部安装行为可用删目录回退。身份和独占归属核实后使用固定供应商卸载配方清理，身份不足、共享、占用、额外权限或重启需求时保留并报告。Python / Miniforge 的成功、错误版本清理、中断恢复均已在隔离 VM 实测；真实重启需求未触发。安装器返回 3010 时记录 `metadata.reboot_required=true` 并提示必须单独确认重启，不自动重启。 安装与卸载返回码分别持久化；只有已记录3010且核实Windows启动时间晚于该次动作后，才解除对应重启前提。卸载阶段还要求供应商记录回到基线。未知卸载结果不自动重放，旧记录缺历史证据时保留并报告；安装重启完成不等于已卸载。成功后按原任务生成新建环境方案，实际重新规划基础解释器路径。

## 平台维护

- import-wsl：name、project、archive（rootfs TAR）、sha256，目标在 env_root 下。系统需已支持 WSL2；命令不自动启用系统功能或重启。
- pull-image：source 必须含 sha256 digest、project。Docker 自身正常数据目录存储镜像。
- create-container：resource_id 指向已登记本机镜像，name、project；默认停止状态，不挂宿主目录、不映射端口、不启用特权；`--pull never` 防止创建步骤隐式拉取。
- start/stop：resource_id 指向具体容器。执行后再次检查真实运行状态。
- delete：容器要求备份文件+SHA256 或非空迁出目录，以及备份完整性的 Agent 条件；文件存在与哈希不代表能自动证明业务数据备份完整。WSL 删除不生成 AIRoot 维护方案。

每次使用 Docker 前重新检查只指向本地 named-pipe。WSL 登记保存当前用户注册表中的注册 GUID 和存储路径用于身份变化检测；但 WSL 注销命令仍按可复用名称寻址，核验与注销之间存在无法消除的竞态。因此 AIRoot 在方案生成和旧方案执行前均拒绝 WSL 删除。用户须在 AIRoot 外重新核对目标并自行操作；备份/迁出确认不构成身份绑定保证。

## 脚本与 MCP JSON

先通过 env list 获取解释器父资源 ID。registry add 的文件采用完整资源结构：

```json
{
  "id": "new",
  "class": "tool",
  "kind": "script",
  "name": "convert-audio",
  "path": "D:\\tools\\scripts\\convert.py",
  "entry": null,
  "version": null,
  "parent_id": "已登记解释器ID",
  "scope": "host",
  "status": "unverified",
  "projects": ["audio"],
  "dependencies": [],
  "metadata": {"reusable": true},
  "updated_at": ""
}
```

`registry add` 会重新分配/合并稳定标识，不信任输入的可用状态。脚本需要实际文件、可用解释器和复用声明，验证后记录脚本及解释器哈希。

MCP 连接器把 kind 改为 `mcp-connector`，metadata 使用 `{"transport":"stdio","args":["D:\\tools\\server.py"]}`，父资源关联已安装解释器/服务程序。当前握手验证协议 2024-11-05；其他协议版本、远程 HTTP、交互会话转发未实现。连接器不是普通一次性 run 命令，Agent 外部启动前使用 usage acquire/release。

## 故障状态

| 状态 | 后续行为 |
|---|---|
| planned | 尚未执行，可核实条件后 apply |
| executing | 后台正在执行，查询 operation show |
| completed | 执行、验证、登记全部成功 |
| failed | 查看各阶段状态；可能有待核实安装，不能一概重装 |
| registration_failed | 外部工作成功，补登记；重复 apply 被拒绝 |
| interrupted | 后台中断，核实实际资源及使用保护，不重放旧操作 |

`usage release <ID> --descendants-checked` 是 Agent 的核查断言；PID/创建时间仍会重新检查。不能仅因过期时间解除保护。

当前源码的安全补丁禁止用此命令提前释放维护操作持有的保护，返回 `OPERATION_RECOVERY_REQUIRED`。需要等待活动维护结束，或对中断操作使用 `operation recover <ID>`／`operation cleanup <ID>` 核实后收尾；`--descendants-checked` 不替代操作结果提交。旧租约通过操作记录中的反向关联核实归属，记录不可读时保留保护。先前交付的安装包不包含此补丁；后续包以单独精确指纹验收为准，源码修复轮次见 `evidence/0.1.1-usage-release-barrier.json`。


## 0.1.1 恢复与清理

```powershell
airoot --json operation recover <操作ID>
airoot --json operation cleanup <操作ID>
airoot --json operation show <操作ID>
airoot --json scan status <扫描ID>
airoot --json status
```

recover 核实实际结果，修复登记或处理已确认失败的独占残留；cleanup 只重试该操作残留清理，不能用来删除正常资源或任意路径。两者异步返回，重复查询 show 直到 recovery.status 不为 running。

旧字段含义保持：status / execution_status / verification_status / registration_status 仍表达原维护结果。新增 reliability.recovery 和 reliability.cleanup 各自含 status、reason、completed_steps、attempts；owned 含 path、identity、purpose、removed；failure_confirmed 表示是否有确定失败证据。原 error 不被清理错误覆盖。

恢复 completed 仅表示核实/处理完成。例如依赖修改失败但已核实当前状态，原 status 仍可为 failed。cleanup.completed 不代表原安装成功。受阻原因通过 reason 返回，不自动扩展对象、来源、位置或权限。

scan.coverage.state 为 in_progress / partial / supported_signatures_checked / unknown，queue_complete 与覆盖结果分别解释；uncovered 记录未覆盖范围或原因。providers 按来源和根目录报告 candidates / truncated / reason / fallback。旧扫描没有覆盖证据时为 unknown，不能从 completed_with_gaps 推断全机不存在其他工具。

`resource.find` 的登记表命中返回 `coverage=registry`。有范围补查时，`complete` 仅在队列耗尽且没有任何跳过或冲突时为 true；否则结合 `uncovered` 与 `skipped` 报告部分结果和具体缺口。`complete=false` 不是“没有匹配”，已返回的 matches 仍然有效。

status.recovery_operations.pending 表示仍需核实的操作数，blocked 表示恢复或清理受阻数，两者可能重叠。出现损坏日志或数据库恢复 notice 时，保留原件并暂停自动维护恢复；显式 recover 仍须逐项核实，不凭备份释放保护。


### 2026-10-28：登记核实/恢复的请求保护（源码补丁）

- `registry restore <ID>` 核实忽略实例时，先获取涵盖关联环境和路径的写保护，再启动探测。关联资源正在使用或维护时拒绝恢复；外部探测期间，查询命令仍可使用。
- `registry verify/restore` 的租约归属于整个核实请求。即使当前版本探测已经退出，通用 `usage release` 仍返回 `VERIFICATION_IN_PROGRESS`，不能在依赖核实或登记提交之前解锁。
- 请求失败时保留磁盘租约并标记 `needs_review`；探测进程与 job 信息随每次启动持久化。待请求真正结束后，须核实进程、相关后代及实际登记状态，再通过既有显式复核流程解除保护。不凭超时、进程主 PID 退出或后台重启自动释放。
- 如果恢复登记已提交而备份失败，资源可能已经受管，但保护仍保留。应先查询实际登记，不应将报错理解为“仍然忽略”，也不能盲目重跑安装或删除。
- 本轮未新增授权模式、未改 Agent SKILL。此前维护操作的 `OPERATION_RECOVERY_REQUIRED` 屏障仍然有效；当前发行安装包的已有维护屏障与这次尚未打包的登记请求屏障应分别看待。

- 验证请求的初始持久意图直接标记 `verifying`，即使还没启动首次探测，也不写成无法通过既有命令复核的孤儿 `reserved`。请求存活时仍由请求屏障禁止手动释放；后台退出后仍保留磁盘保护，必须显式复核才可释放。PID 为空不能证明没有遗留进程，通用及维护操作的 `reserved` 规则没有放宽。
