# AIROOT 受保护签发方方案（草案）

**状态：已裁决 —— 不做（ADR-0044）。本文保留为那次裁决的依据，不再是一份待批提案。**

裁决的结论是：**没有密钥、没有签发方、没有 keyring 迁移、没有算法变更。** 理由不是"太难"，而是
§2 的实测与 §3 那条推论合起来说明**目标里那条性质在本机做不到**，而三条候选路没有一条能兑现它。
裁决本身（含被否决的三条路与后果）见 `docs/AIROOT-v0.3-实现决策记录.md` 的 **ADR-0044**。

本文继续回答那个问题：**「私钥的受保护存放」这一步，边界到底在哪里，能做什么、不能做什么。**

它是 `docs/broker/AIROOT-受保护Broker方案-v1.md` §5（Approval token 规则）与 §9（不属于本方案的内容）之间那段空白的填充提案。§9 明确写着：

> 本方案不规定真实签名密钥的部署、企业级审批 UI、Everything 私有接口或完整 Windows 服务安装包。

这一步就是「真实签名密钥的部署」。它目前**没有任何设计**，而 ADR-0039 的后果一节把它列为"真实私钥今天没有任何被保护的家"。

---

## 1. 为什么这一步不能直接开工

五份权威文档各写了一句，合起来把这一步锁得很死。**先把锁列清楚，因为任何绕过它的方案都是假的。**

| 出处 | 原话（要点） | 对设计的约束 |
|---|---|---|
| `tx/approval.py` 模块文档 + ADR-0039 决策三 | 核心**永远不会有签名侧**——那是"CLI 不能凭空制造同意"的实现方式 | 签发代码**不得**进入 `cli/app/airoot` 的任何被 CLI 动词可达的位置 |
| `crypto/ed25519.py` 文档 + 草案 §113.6 第 6 条 | `sign` 处理私钥且**不是常数时间的**；标量乘的加法链跟随**私钥**的位；**"没有任何无分支改写能修好它"**；"长期签发密钥**不得**由本模块签" | **纯 Python 的签发方被明确否决**，且该否决**不**是"以后优化一下就行" |
| ADR-0025 的 D1（选 A） | 否决了"现在就做真实 `ed25519`"：在没有受保护存储的机器上做，等于把"私钥就放在 root 里"变成事实上的设计，还给它披上"已签名"的外衣 | **"先随便存起来、以后再保护"这条路被明文否掉** |
| ADR-0039 决策五 | 验证强度上限等于它的 keyring，而今天 keyring 是 root 里的一个文件，**任何能写 root 的进程都能换掉它** | 换掉私钥的存放**不足以**修好这条路：**信任锚本身**（keyring）也必须不可被同用户进程改写 |
| `cli/schema/approval-token.schema.json` | `signature.algorithm` 的 enum 只有 `ed25519` 与 `test_hmac_sha256`；`schema_version: 1` 是唯一主版本 | 换算法要有新的 schema id，等于改已发布契约 |

**两条硬约束：**

1. 签发动作必须发生在一个**私钥永不进入 Python 进程**的地方。否则 §113.6 第 6 条被违反，而且这是**技术上**不可修的违反。
2. 算法必须是 **`ed25519`**。所以这条路成立的前提是：**这台机器能用一个非导出、由 OS 持有并执行 Ed25519 签名的密钥。**

---

## 2. 实测：这个前提**不成立**

**未裁决前设计的路线是「OS 持有非导出密钥、Python 只请求签名」（CNG / NCrypt）。实测把它否掉了。**
测量在一台 Windows 10 Pro build 26200 上，用 `ctypes` 直接调 `ncrypt.dll`，探测脚本自清理（见 §2.3）。

### 2.1 入口点与算法可用性

| provider | 算法 | 结果 |
|---|---|---|
| Microsoft Software Key Storage Provider | `ED25519` | **`NCryptCreatePersistedKey` 失败 `0x80090029`（`NTE_NOT_SUPPORTED`）** |
| Microsoft Software Key Storage Provider | `ECDSA` + nistP256 | create ok，finalize 失败 `0x80090027` |
| Microsoft Software Key Storage Provider | `ECDSA_P256` | **create + finalize + sign 全通**，签名 64 字节 |
| Microsoft Platform Crypto Provider（TPM） | `ED25519` | **同样失败 `0x80090029`** |
| Microsoft Platform Crypto Provider（TPM） | `ECDSA` / `ECDSA_P256` | **create + finalize + sign 全通**，签名 64 字节 |

七个入口点（`NCryptOpenStorageProvider`/`CreatePersistedKey`/`FinalizeKey`/`SignHash`/`ExportKey`/`DeleteKey`/`FreeObject`）全部解析成功；两个 provider 都存在，**包括 TPM provider**。

**结论：这台机器的 CNG 不支持 Ed25519，两个 provider 都不支持。** 而 schema 只允许 `ed25519`（`test_hmac_sha256` 按 `docs/schema/README.md` 只许出现在假切片里，且它是共享密钥、不是签名）。

### 2.2 非导出的确做到了（这一半是成功的）

对两个 provider 都试了取私钥：`NCryptExportKey(PRIVATEBLOB)` 分别以 `0x80090029`（软件 KSP）与 `0x8009000A`（TPM KSP）**被拒**。所以"让 OS 持有不可导出的密钥、Python 只递哈希取签名"这个**机制**在本机是通的——**它只是不支持我们需要的那个算法**。

### 2.3 清理证据

探测前后，用户密钥容器目录 `%APPDATA%\Microsoft\Crypto\Keys` 的文件数都是 **47**，无残留。

### 2.4 顺带量到：同用户进程读得到容器里的密钥

```
icacls "%APPDATA%\Microsoft\Crypto\Keys"
  PC-…\<user>:(I)(OI)(CI)(F)     ← 跑这段代码的正是这个 token
  BUILTIN\Administrators / SYSTEM:(F)
```

软件 KSP 的密钥容器对**拥有者 token 完全开放**。这解释了一件事：即使 CNG 支持 Ed25519，**软件 KSP 对"同用户进程"也不构成保护**——拥有者能读那个目录。§3 说明这不是配置问题。

## 3. 真正的障碍：目标里那条性质在本机**做不到**

目标的原话是"私钥有一个真正受保护的家（**不可被用户自己的进程读取**）"。**实测否掉了它，而且否掉的方式与 CNG 无关。**

理由是一条不需要实验的推论，但它值得写清楚，因为它是这一步的**全部难点**：

> **任何"用户自己的进程能用来签名"的密钥，那个进程（以及任何以同一用户身份运行的进程）都能读。** 若签发方是用户进程可调用的，那么它以用户身份读取密钥；既然是同一身份，另一个进程也能读同一份东西。AGENTS.md §5 那句"v1 不是能对抗管理员权限的安全产品"在这里有一个更弱的版本：**它也不对抗同一用户身份**。

三条推断，各自否掉一类方案：

1. **文件式密钥库（包括"放一个只有 Administrators 能读的目录"）**：签名者若是用户进程，它读不到那个文件——所以它签不了；它若读得到，攻击者作为同一 token 也读得到。**ACL 只能把"能签名的人"和"能读密钥的人"设成同一个人。**
2. **OS 持有的非导出密钥（CNG 软件 KSP）**：实测容器对拥有者开放（§2.4），同一 token 可读。CNG 买到的性质是**不可导出**（密钥字节不能被拷走），**不是**"同用户进程不能用它签名"。
3. **DPAPI / 用户级加密**：以用户身份运行的任何进程都能解密。它保护的是"磁盘被拷走"，不是"同一台机器上的同用户进程"。

**唯一两条能真正把"同用户进程"挡在外面的路**，都不在 CNG 里：

- **需要一个人才知道的秘密**（口令短语 / PIN）。密钥在静态时由它保护，签发时才解锁。这才是"用户自己的进程读不到"的**唯一**技术实现。
- **一个 OS 强制的权威边界**（提权 + 受保护服务，或 TPM 的授权策略）。但注意：本机的 TPM provider 密钥仍可由同一用户调用（§2.1），所以**即使走 TPM，"谁能请求签名"仍要靠 elevation 来约束**——TPM 加的是"密钥不能被拷走"，不是"同用户不能签"。

## 4. 三条候选路，与它们的代价

### 路 1：扩展 schema，改用 `ECDSA_P256`，把密钥放进 CNG/TPM（非导出）

本机**技术上立刻可行**（§2.1 已签出 64 字节签名），且拿到真实"不可导出"。
**代价**：`approval-token.schema.json` 的算法 enum 是**已发布契约**，扩它要新 schema id、要改 `docs/schema/README.md` 的边界表、要重生 golden 语料，并且**推翻**草案里"生产算法是 ed25519"的既有表述。ADR-0003 只为 `reference-plan` 破过一次例。
**但它仍不满足原目标**：密钥对拥有者 token 可读（软件 KSP），同用户进程仍能签名（除非再加路 2 或路 3）。

### 路 2：口令短语解锁的 Ed25519 签发方（算法的 schema **不用改**）

私钥静态加密（`scrypt`/`PBKDF2` + AEAD），只有人输入口令才解锁；解锁后由纯 Python 在**内存**里签。
**代价**：违反 §113.6 第 6 条（非常数时间签名）。**这是真正的取舍**：要么承认这条约束在本机无解而放宽它，要么这条路不存在。

### 路 3：承认"私钥的受保护家"在 P2 的 Python 阶段做不到，**如实记录**，把签发方留给 Rust

与 ADR-0025 的 D1 完全一致（它选的正是这个）。
**代价**：`approve`/`install`/`env persist`/`gc --apply`/`uninstall` 五条路径继续走不到底；**Rust 切换本身要 stage/commit，而 stage/commit 要批准**——所以这条路在 P2 内不闭环，必须明说。

---

## 5. 我的建议

**路 3 为默认，外加一件与它不冲突、且今天就能做完的事。**

私钥的家做不成，但**信任锚的完整性**是另一件事，而且它有真实的、可测的改进空间：

- 现在 `state/test-keyring.json` 的唯一写者是测试签发方，**名字本身就在说它是测试件**；
- ADR-0039 决策五说验证强度等于 keyring，而 keyring 可被任何能写 root 的进程换掉。

所以在边界存在之前可以落地的是：**给 keyring 一个生产形态（路径、格式、校验、只读语义、以及"它的完整性仍等 ACL 强制"的显式标注），并让加载期**能**检出被替换**（例如一个由调用方钉住的期望指纹，而不是取自被检查的目录）。这满足"生产 keyring"那一半目标，且**不**假装私钥已受保护。

至于算法与密钥存放（路 1 / 路 2），**我不建议现在改已发布契约**：那是一处需要单独裁决的语义变更，而且无论选哪条，只要不同时解决"同用户进程能否请求签名"，它都买不到目标里那条性质。

---
