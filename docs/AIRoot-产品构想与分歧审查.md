# AIRoot：产品构想与分歧审查

版本：v0.76（首版范围已补充）  
更新日期：2026-10-18  
状态：已按最新决定整理首版范围与验收清单，见同目录《AIRoot-首版范围与验收清单.md》；本文件保留决策与历史审查记录。暂不编写 SKILL，未确认建议不自动获准。

## 一、构想的核心

AIRoot 有两大部分：**登记表**与**维护扳手**。

登记表让 Agent 快速知道本电脑有哪些环境和工具、在哪里、怎样使用；维护扳手封装 conda、pip、Python 脚本等底层操作，让资源的发现、安装、升级和删除与登记联动。

目标是把基础资源管理好，方便 Agent 在此基础上完成任务，而不是每次重新寻找、重复安装。

## 二、用户已经明确的要求

### 1. 两张登记表，未来允许扩张

- **环境表**：登记本电脑的环境，包括 conda 中的各个虚拟环境、各个 venv 等。
- **非 Python 环境也纳入产品范围**：Node.js、Java、WSL、Docker 等相关运行环境纳入登记和维护；各类资源的具体登记单位与归属表仍待明确。
- **工具表**：登记有工具性质的资源，例如 ffmpeg、各种 CLI、Blender。
- QQ、微信，以及 Chrome、VS Code、Excel 这类普通软件，默认不收录到工具表；若通过已安装的第三方 MCP 连接器供 Agent 操作，允许作为工具收录。
- 用户以 Blender 为工具收录示例，并提出软件是否开放 MCP 作为判断边界；明确属于软件且不具备其所指 MCP 开放能力的，不收录为工具。
- ffmpeg、各种 CLI 原有的收录范围保留；本轮不将 MCP 擅自扩展为所有工具的必备条件。
- 已确认第三方 MCP 接入也满足收录条件，不要求软件原生提供 MCP；本轮场景是已安装连接器、Agent 能通过它操作软件，不扩展为只要网上存在连接器就自动收录。软件本体与 MCP 连接器在同一张工具表内分别登记，并记录两者的关联及调用方式。
- 用户自制实用脚本也纳入工具表：具有明确调用方式，能独立完成实用功能并可重复使用，登记时关联所需环境。普通项目源代码和临时测试文件不因脚本扩展名而自动收录；用途不明时不直接认定为工具。
- 自制实用脚本缺少运行依赖时，先登记脚本及已知运行要求，标记为“缺少依赖／暂不可用”，扫描时不直接补装。任务真正需要时，再按既定环境选择、安装授权和兼容性规则准备环境及依赖，验证成功后更新为可用；不确定的依赖要求标为待核实，不凭猜测安装。
- 非 Python 环境如何细分登记，后续再定。

### 2. 首次发现与遗漏补登记

- 初次安装 AIRoot 时，允许投入时间搜查电脑，登记已有环境和工具。
- 首次扫描默认覆盖全部本机磁盘，包括其他 Windows 用户的个人目录，不按账户默认排除；不纳入外接盘和网络盘。
- 全扫指发现范围，登记对象仍限于已确认的环境和工具；遇到无权访问的目录按第 22 条记录并跳过，最后集中说明，不自行更改目录权限。
- 首次搜索可能遗漏资源。
- 发现遗漏后，用户可以说明位置或对象，调用扳手补登记。
- 已有资源不必先经过 AIRoot 安装，才能被登记。

### 3. 安装与删除都联动登记

- Agent 或用户需要安装环境、工具时，调用维护扳手安装并登记。
- Agent 或用户需要删除环境、工具时，调用维护扳手删除实际资源以及对应登记。
- 删除失败、部分删除或结果不明时保留登记并记录实际状态，核实删除成功后才移除对应登记，详见第 30 条。

### 4. 任务途中可以补齐或升级资源

- Agent 不必等任务结束，才安装或升级需要的环境、依赖或工具。
- 普通权限下，由调用 AIRoot 的 Agent 向用户发起授权请求。
- 用户同意一次安装，只授权该次请求，不代表授权整个任务后续的其他安装；后续新增安装需求需要单独询问。
- 用户开启 Full Access 时，任务所需的安装、升级直接执行，不再额外询问。
- AIRoot 只标记操作为高风险或低风险，不读取或管理 Agent 的权限模式；是否请求授权由调用方 Agent 决定。Full Access 指该 Agent 中开启的模式。
- AIRoot 无需获取调用方权限状态，因此不设置“获取不到状态时怎么办”的权限回退规则。
- 完成资源准备后，应继续原任务，而不是把安装本身当作任务终点。

**权限边界提醒：**Full Access 下任务所需安装、升级免确认，但不允许 Agent 自行清理旧环境。用户笼统要求清理时，先列出候选环境及对应项目，由用户确认删除哪一个或哪些。持久环境变量及默认命令修改需明确确认，见第 40 条；降级及其他共享环境、系统配置修改的未定细则仍待讨论。

### 5. 新任务与旧环境冲突时，新建环境

- 当新任务需要的升级可能影响旧项目运行时，新建环境，保留旧环境。
- 若升级前无法准备可靠的恢复方式，同样改为给当前任务新建环境，保留原环境；遵循已有命名、项目关联、安装位置和权限规则。
- 新环境以新任务的简称命名。
- 环境登记中记录对应项目。
- 在 Full Access 下，这种新建环境操作直接执行，无需再次请求授权。
- 本条针对有兼容性冲突的场景，不表示每个新任务都必须创建环境。
- 已确定需要新建环境时，若任务简称重名，自动添加未占用的数字后缀（如 `video-2`、`video-3`），登记实际名称及对应项目，不覆盖已有环境，也无需单独询问名称。创建环境本身仍遵循既定权限规则。
- 没有明确项目的临时任务，归属登记为“临时任务”，记录任务简称、用途和创建时间；有明确工作目录时一并记录，无需为了填写项目而打断任务。环境仍按任务简称命名，并遵守不主动清理的规则。
- 安装位置遵循第 13 条。

### 6. 不主动清理，在任务完成后提示

- 即使开启 Full Access，Agent 也不允许自行清理旧环境。
- 当发现旧环境可能需要清理时，在当前任务完成后提示用户。
- 提示本身不构成删除授权，不得据此删除资源或移除对应登记。
- 用户笼统要求清理时，主动列出候选环境及各自对应项目，由用户确认删除哪一个或哪些。
- 只删除用户确认的环境，并联动处理对应登记；Full Access 不省略上述对象确认。
- 失败安装产生的临时资源如何处理，仍待确认。

### 7. 已有环境允许按相同规则补装依赖

- 对扫描登记、原本由用户手动创建的环境，在不影响旧项目的前提下，Agent 可以通过维护扳手补装任务所需依赖。
- Full Access 下直接执行；普通模式下由 Agent 请求本次安装授权。
- 不因环境并非 AIRoot 创建而额外限制上述补装；若修改可能影响旧项目，仍按既定规则新建环境。
- 本轮确认的是已有环境补装依赖，不推定所有已有软件的修改或卸载细则都已确认。

### 8. 环境记录包含依赖包及版本清单

- 在环境条目下附带已安装依赖包及版本清单，供 Agent 按需查看和选择环境。
- 普通依赖包不单独占工具表条目；其中符合工具定义的 CLI 仍可独立登记。
- 扳手完成安装、升级或卸载后，更新受影响环境的依赖包及版本清单。
- Agent 下次准备使用某个环境时，先核对并更新该环境的实际依赖；只检查选定环境，不因此重新扫描全盘。
- 用户在 AIRoot 之外手动改动依赖，也通过上述使用前核对同步到登记。
- 各类环境的具体采集范围仍待确认。

### 9. 路径失效且原因不明时保留登记

- 发现登记中的环境或工具路径不存在，但无法确定原因时，保留记录，标记为暂不可用，并记录已发现的问题。
- 删除、移动、外接盘未连接等可能性未经核实，不作为确定原因写入。
- 此类记录需由用户确认后再移除。
- 用户已确认删除且扳手执行成功的资源，仍按既定规则同步移除登记。

### 10. 历史环境项目归属未知时先登记

- 首次扫描发现旧环境，但缺少足够依据确定对应项目时，先登记，项目归属标为未知。
- 扫描完成后集中列出，供用户按需补充，不逐个打断扫描要求填写。
- 不把根据环境名称作出的猜测写成确定的项目归属。
- 新建任务环境仍须记录对应项目。

### 11. 搜索组件必须随 AIRoot 装载

- 用户确认此前讨论的搜索组件属于必须装载的基础能力，Everything 将嵌入 AIRoot 项目；取消将其作为用户可选加速组件的建议。
- 按本轮上下文，必装载组件范围包括 PET、Everything 及调用接口、fd。具体版本和接口选型在实现时确定，ES 与 SDK 是否都需交付尚未决定。
- AIRoot 负责这些组件的准备与接入，作为产品整体提供搜索能力。
- 必须装载不等于所有组件每次都同时执行；各组件负责的搜索阶段及后备扫描触发条件仍需设计。
- 扫描范围仍仅本机磁盘。首次发现、验证、登记及依赖采集的具体调度尚未全部确认。
- 已确认搜索组件随电脑开机启动，并常驻后台维护文件名索引，即使没有 Agent 正在执行任务。此确认针对索引维护，不表示所有搜索组件持续扫描或不断采集全部依赖。
- 内嵌 Everything 是 AIRoot 不可分割的一部分。无论电脑是否已安装 Everything，AIRoot 始终使用自身内嵌版本，不检测并选择复用外部版本，也不将其作为回退来源。
- 内嵌版本与用户另行安装的 Everything 独立运行和管理；配置、索引及调用应保持隔离，具体实现方式待验证。
- 卸载 AIRoot 时一并移除自身内嵌搜索组件、专属开机启动项及文件索引缓存；所管理的项目环境和工具保留，登记表与项目关联默认保留，见下条。

### 12. 卸载 AIRoot 时保留项目资源及登记数据

- 卸载 AIRoot 时，保留它管理的所有项目环境和工具，包括通过 AIRoot 安装的资源。
- 删除这些资源仍需用户单独明确指定，卸载 AIRoot 本身不构成删除授权。
- 卸载时默认保留两张登记表及用户补充的项目关联，供以后重装时恢复；恢复时核对资源的实际状态。用户明确要求清除登记数据时再删除。
- 卸载时停止并移除 AIRoot 自带的搜索组件（包括内嵌 Everything）、专属开机启动项和文件索引缓存；不影响用户另行安装的 Everything。

### 13. 信息集中存储，环境与工具沿用正常维护位置

- AIRoot 的所有自有信息集中存储在 C 盘当前用户目录下的 `.airoot`，即 `C:\Users\<用户名>\.airoot`。包括登记表、项目关联、配置、日志及内嵌搜索组件产生的索引等信息，不在其他目录分散存放。
- `.airoot` 只存信息，不存环境或工具本体。AIRoot 程序本体和内嵌 Everything 的安装位置由用户在安装时指定；运行产生的自有信息仍统一存入用户目录 `.airoot`。
- 环境与工具使用正常维护位置，例如本机的 `D:\env` 和 `D:\tools`；不额外建立 `AIResources` 或其他 AIRoot 专属资源总目录。
- 已有资源保持原位置，不为统一目录而搬迁；新环境和工具遵循用户现有或指定的维护位置。D 盘路径是本机示例，不推定其他电脑也使用 D 盘。
- 如果所需的 `env`、`tools` 目录不存在，主动询问用户是否在某个盘初始化对应目录，获得确认后再创建。不因 Full Access 而跳过这次用户明确要求的询问；授权仍由调用方 Agent 管理。
- 目录初始化的确认不改变此前已确认的任务安装规则。本轮仅记录产品要求，不执行目录创建、迁移或安装。

### 14. 多个已有环境可用时的选择顺序

- 用户未指定使用哪个环境时，优先选择当前项目已经关联且满足需求的环境。
- 没有合适的项目环境时，允许 Agent 自动选择其他无需修改依赖就能完成任务的已有环境，无需逐次询问使用哪一个。
- 选择前仍按既定规则核对实际依赖；补装、升级及可能影响旧项目的操作仍遵循已有兼容性与权限规则。
- 同一环境允许关联多个项目；实际被新项目复用后，自动追加该项目并保留原有关联。仅被搜索到或考虑过的候选环境不追加关联。
- 后续升级前检查对所有已知关联项目的影响；列出清理候选时同时展示所有已知关联项目。
- 同名工具多版本的选择规则见第 18 条。

### 15. 使用中的环境和工具禁止其他 Agent 修改或删除

- 环境正在被使用期间，其他 Agent 不能对其补装依赖、升级或删除；Full Access 下同样适用。
- 工具同样适用：正在执行任务的具体工具实例，其他 Agent 不能升级、覆盖或删除，即使开启 Full Access。可以等待，或在确认相互独立且不影响当前任务的前提下，按既定安装规则另装一份。
- 工具异常退出后的使用标记按环境的规则处理：核实相关任务和工作进程均已结束才解除对应标记，无法确认时保留保护并提示。
- 需要变更的任务可以等待使用结束，或按已有规则另建环境；删除仍须用户明确确认。
- 此规则属于资源使用约束，不改变 AIRoot 标记风险、调用方 Agent 管理授权的职责划分。
- Agent 意外退出后，确认相关任务及使用该环境的工作进程均已结束，自动解除对应使用标记；无法确认时保留保护并提示用户。不仅凭 Agent 失联或经过一段时间认定环境空闲。
- 解除使用标记本身不授权修改或删除；其他仍在使用该环境的任务继续受到保护。
- 使用状态的具体识别方式，以及等待后何时执行，仍待确认；尚未实现或验证并发控制。

### 16. 新环境和工具安装失败时保留状态记录

- 新环境或工具安装失败时，保留登记并标记为“安装失败／未完成”，记录目标位置、已知失败原因及已发现的残留情况。
- 未完成的资源不作为可用资源推荐给 Agent；安装成功并通过基本可用性验证后，再更新为可用。
- 已获授权的安装因临时网络中断失败时，在安装目标、版本、来源和位置不变，且不涉及删除或扩大修改范围的前提下，允许自动重试最多两次，无需重新询问；仍失败则记录结果并提示用户。
- 重试的授权判断由调用方 Agent 负责；新增安装需求仍遵循既定授权规则。
- 安装失败留下的残留允许自动清理，无需再向用户询问，不以开启 Full Access 为前提。这是失败安装的收尾，不改变旧环境不得主动清理的规则。
- 自动清理限于能确认属于此次失败安装的残留，不扩大到原有环境、工具、项目文件或其他资源共用的文件；不能确认归属时不得按失败残留直接删除。
- 清理后同步记录实际结果：清理成功则在失败记录中注明残留已清理；未清理成功则记录剩余位置和原因。保留此前确认的失败记录，不将已清理的资源标为可用。
- 已有环境升级失败后的恢复遵循第 17 条。

### 17. 已有环境升级失败后自动尝试恢复

- 升级前记录原状态并准备可行的恢复方式；获准的升级失败后，在恢复范围明确且不影响其他正在运行任务的前提下，自动尝试恢复升级前状态，无需为该恢复另行询问。
- 恢复后进行验证并更新登记；无法恢复或验证未通过时，标记异常并提示用户，不继续作为正常环境使用。
- 本条不改变可能影响旧项目时新建环境、使用中的环境禁止其他 Agent 修改等既定规则。
- 升级前无法准备可靠恢复方式时，改为给当前任务新建环境并安装所需版本，保留原环境；遵循既定命名、项目关联和安装位置规则。普通模式下新增的新建安装请求由 Agent 单独申请授权，Full Access 下按任务需要执行。
- 具体恢复能力尚待实现验证，不承诺所有升级都能还原。

### 18. 同一工具存在多个版本时的选择顺序

- 用户或项目明确指定版本时，遵循指定；无法满足明确要求时按既定规则处理安装需求，不擅自替换为其他版本。
- 没有明确指定时，优先沿用当前项目已经使用且仍满足需求的版本。
- 没有项目使用记录时，由 Agent 从已登记且验证可用的版本中自动选择满足任务需求的一份，无需逐次询问使用哪个版本。
- 工具实际被项目使用后，在对应工具记录中自动追加该项目，保留原有关联；同一工具允许关联多个项目。记录使用时的版本和路径，区分不同安装。
- 仅搜索到或考虑过、未实际使用的候选工具不追加关联。项目关联供版本选择、升级影响评估和清理候选展示参考，不把历史使用直接等同于永久依赖。

### 19. 工具升级可能影响旧项目时保留旧版

- 新任务需要新版工具，但替换旧版可能影响已有项目时，若支持多版本独立安装和调用，则保留旧版，在正常工具维护位置另装新版，分别登记并让各项目使用对应版本。
- 安装新版仍遵循既定权限规则；本条不授权删除旧版本。
- 无法多版本共存时，先说明影响并询问用户，再决定是否替换；即使开启 Full Access 也不直接覆盖旧版。

### 20. AIRoot 之外新增的环境和工具自动补登记

- 用户通过其他方式创建环境或安装工具后，AIRoot 在本机磁盘范围内发现新增候选，核实符合收录条件且安装或创建已完成后，自动补登记，无需用户主动提醒或逐项确认。
- 项目归属无法确定时标为未知，保持资源原位置；新增资源仍须符合既定环境和工具收录范围。
- 有依据确认可用后才标记可用，不能只凭文件名认定；发现频率及具体方式留待实现设计，不要求持续全盘扫描。
- 本条确认自动发现和登记，不将其扩展为自动执行来源不明程序、修改资源或搬迁文件的授权。

### 21. 资源移动后核实身份并更新路径

- 原登记路径失效，在本机新位置发现资源时，有充分依据确认是同一资源后，自动更新当前登记路径、保留项目关联，并记录旧路径供追溯。
- 更新路径后重新检查可用性；不能仅因发现新位置就标记资源正常。
- 只有同名或无法确认身份时，不自动合并；保留原记录并标为暂不可用，提示用户确认。
- 本条允许更新登记，不包括自动修复资源内部路径或修改项目配置。资源身份判断的具体方式留待实现验证。

### 22. 扫描无权访问的目录时先记录并跳过

- 扫描遇到当前权限无法读取的目录时，记录路径及原因，先跳过并继续扫描其他位置，不逐个中断扫描。
- 扫描结束后集中说明尚未扫描的范围，不将无权访问的目录记为已扫描或据此断言没有资源。
- 后续补扫的授权仍由调用方 Agent 按既定权限机制处理；不为扫描自行更改目录权限。

### 23. 默认下载来源与更换镜像

- 用户或项目已明确指定下载来源时，先遵循该要求；未指定时，优先使用官方发布渠道或包管理器的默认源。
- 登记实际下载来源，遇到下载困难不自行换成来历不明的下载站。
- 改用尚未获用户认可的第三方镜像时，由 Agent 单独向用户确认，Full Access 同样适用。
- AIRoot 仍只提供高低风险标记，授权由调用它的 Agent 管理。

### 24. 新增付费必须单独确认

- 涉及新增付费的操作由 AIRoot 标记为高风险，Agent 说明用途、已知费用及是否有合适的免费替代方案。
- Agent 必须单独取得用户对这笔费用的明确同意后再继续付费步骤；Full Access 不视为支付授权。
- 已有可用许可且不产生新增费用时，沿用正常安装流程，不因工具属于付费产品而重复要求购买确认。

### 25. 大体积下载与长时间安装提前告知

- AIRoot 提供可获得的下载量、预计空间占用及耗时信息，由 Agent 提前告知用户；无法可靠估计时说明未知。
- 普通模式将上述信息包含在本次安装确认中，不重复询问；Full Access 下告知后直接继续，不仅因下载体积大或安装耗时长而额外要求确认。
- 新增付费、更换未获认可的第三方镜像等既定单独确认规则仍适用。
- 具体提醒阈值尚未确定。

### 26. 目标磁盘空间不足时先确认新位置

- 暂停受影响的安装，由 Agent 说明空间不足及可用位置，让用户决定是否改到其他磁盘或目录；Full Access 同样适用。
- 替代位置需要初始化 env 或 tools 文件夹时，可与换盘一并确认。
- 本次改换位置不自动改变以后安装的默认位置。
- 不擅自删除已有环境、工具或其他文件来腾空间；失败安装残留仍按既定规则处理。

### 27. 工具本体的安装位置例外需单独确认

- 工具本体无法安装到指定目录时，由 Agent 说明限制、实际安装位置，以及是否有满足任务需求且可安装到指定目录的版本或替代工具。
- 仍需在指定目录之外安装本体时，先取得用户对本次位置例外的同意，Full Access 同样适用。
- 安装成功后登记真实路径，本次同意不自动改变其他工具的默认安装位置。
- 工具自身配置和缓存的位置规则见第 28 条。

### 28. 外部工具的配置和缓存沿用正常位置

- 受 AIRoot 管理的外部工具，其配置和缓存允许沿用自身正常位置；AIRoot 记录能够确认的相关路径，不为统一目录擅自搬动已有文件。
- 不要求外部工具的配置和缓存全部集中到 env、tools 或 .airoot。
- AIRoot 自己的登记表、日志、内嵌搜索组件的索引等信息，仍集中在 .airoot；外部工具的存储规则不扩展为 AIRoot 自身的例外。
- 本条只确认位置原则，不授权清理缓存；安装包临时文件的处理另行审查。

### 29. 删除环境时同步处理内部工具及外部依赖

- Agent 在删除确认前，一并列出环境、关联项目、会随环境删除的工具实例，以及已知会受影响的外部脚本。
- 用户确认这一范围后执行删除；环境删除成功并核实内部工具随之移除时，同步移除这些工具实例的登记，不逐项重复询问。
- 其他环境中的同名工具保留；环境外的脚本保留文件和登记，核实后更新可用状态及依赖问题，不跟随删除。
- 使用中保护规则仍适用；删除失败或结果不明时不能按成功移除登记，异常登记规则见第 30 条。

### 30. 删除未完成或结果不明时保留实际状态

- 删除失败、部分删除或结果不明时，保留对应登记，记录实际状态、已知原因及残留位置，由 Agent 告知用户。
- 只有核实已在本次授权范围内成功删除的对象才移除登记；同批删除多个对象时分别处理。
- 可用性单独核实：部分损坏或无法核实的对象不作为可用资源推荐；确认完整且仍可用的对象如实记录。
- 原授权范围内的有限删除重试规则见第 31 条。

### 31. 原授权范围内允许有限删除重试

- 临时故障解除后，核实仍是原授权对象、残留属于原删除范围且没有任务正在使用，允许在本次删除流程内自动重试最多两次，不逐次询问。
- 不为重试扩大删除范围、强制结束其他任务、改变目录权限或删除归属不明的文件；身份、范围或使用状态无法核实时停止。
- 重试仍失败时保留异常登记并告知用户，不无限重试；本规则不授权后台定时删除。
- AIRoot 提供风险标记，涉及额外权限的处理仍由调用方 Agent 决定。

### 32. 独立工具也不主动清理

- 独立工具沿用旧环境清理原则：即使 Full Access，也不因闲置、版本较旧或存在同名工具而主动删除，可在当前任务完成后提示。
- 用户笼统要求清理时，列出候选工具的版本、路径、关联项目及已知依赖影响，由用户确认具体删除实例，再按既定规则执行并同步登记。
- 没有使用记录不等于没有用途，未知关联如实标为未知。
- 工具卸载时默认保留配置和缓存，清理确认及范围见第 33 条。

### 33. 卸载工具时默认保留配置和缓存

- 在本次卸载确认中说明工具配置和缓存的已知位置及归属，询问是否一并清理；用户未明确同意时默认保留。
- 同意清理后，只处理确认属于本次对象且不被其他版本或工具共用的内容，不扩大到项目文件或归属不明的目录。
- 卸载方式无法保留配置时，提前说明影响，取得同意后再执行，Full Access 同样适用。
- 失败安装残留仍按既定规则处理，不由本条扩大清理范围。

### 34. 支持取消登记并持续忽略指定资源

- 用户可要求取消登记／不再管理，保留实际环境或工具及其配置、缓存，从正常登记及候选推荐中移除。
- 在 .airoot 中保留必要的忽略信息，后续扫描不自动重新登记同一资源，直到用户主动恢复管理，再核实并登记。
- 忽略仅针对选定资源，不因同名而排除其他环境或工具。
- 取消登记不授权终止当前任务或解除使用保护；历史项目关联和备注的保留及恢复规则见第 35 条。

### 35. 取消登记时保留历史关联，恢复时核实后带回

- 取消登记时在 .airoot 内保留历史项目关联和用户备注，不参与正常推荐。
- 恢复管理时核实资源身份、当前路径、版本和可用性；确认为同一资源后带回历史关联及备注。
- 历史关联不保证当前仍兼容，发生变化或无法确认的部分标为待核实，不自动改写项目配置。
- 无法确认是同一资源时，不直接套用旧关联。

### 36. 登记无匹配资源时，安装前先针对性查找

- 不将未登记直接认定为本机未安装；安装前利用已有索引、环境管理器信息和相关位置，进行一次限定范围及时间的针对性查找，不重新全盘扫描或无限等待。
- 找到并核实满足要求的已有资源后，补登记并复用；没找到合适资源时，再按既定规则安装。
- 未覆盖或无权访问的范围如实记录，不声称已证明全机不存在该资源。
- 遵循用户已设置的忽略规则，不重新登记或使用已取消管理的资源；用户明确要求新建独立环境或安装指定实例时仍按要求执行。
- 具体查找时限与实现待定。

### 37. 配套 Agent SKILL 的职责边界

- AIRoot 要配套一个给 Agent 使用的 SKILL；用户明确要求现在先不编写，当前只记录产品设计。
- SKILL 描述通用使用流程：何时查表、如何调用维护扳手、如何处理风险标记，以及哪些情况需要由 Agent 向用户确认。
- 登记表保存本机动态资源信息，如路径、版本、关联项目和工具特有的调用方式；不将两张登记表的具体内容写死在 SKILL 中，由 Agent 按需查询。
- 维护扳手执行具体操作，返回结果并同步登记；AIRoot 标记风险、调用方 Agent 管理授权的职责不变。
- 工具登记是否进一步附带用途说明和最小示例仍待确认；本轮不将 SKILL 的流程说明视为已经实现的权限保障。

### 38. 需要本机资源时按需查询 AIRoot

- Agent 需要选择或使用本机环境、工具时，先按当前需求查询 AIRoot，再使用合适资源；任务中出现新资源需求时，再查询相关部分。
- 按用途、项目、工具名称或版本等需求缩小查询范围，不默认加载整台电脑的完整登记表。
- 纯聊天或无需本机资源的文字任务不强制查询。
- 本条是预期使用流程，具体接入方式仍待实现，不代表任何 Agent 已自动加载或遵守；SKILL 暂不编写。

### 39. 维护扳手尚未支持时允许直接新增安装后补登记

- 仅在维护扳手能力尚未覆盖该安装方式时，允许 Agent 按既定权限、来源、安装位置、兼容性和使用保护规则，直接调用官方安装器或明确的底层命令完成新增安装。
- 成功后由 AIRoot 核实并补登记，记录实际来源、路径、版本及项目关联；失败时如实记录，残留清理遵循既定范围。
- 授权未取得、资源正在使用等限制不能作为改用底层执行的理由。
- 本条不扩展为任意直接升级、删除或修改已有环境，也不授权自动修改 AIRoot 程序以增加新扳手。

### 40. 持久环境变量与默认命令修改需明确确认

- 优先通过登记的具体路径调用资源，或只为当前任务设置所需环境变量。
- 确需持久修改用户级或系统级 PATH 等环境变量、默认命令指向时，AIRoot 标记为高风险，由 Agent 说明影响并单独取得用户同意，Full Access 同样适用。
- 可在本次安装确认中明确列出该变更，不将普通安装许可自动解释为同意修改全局设置。
- 本条仅确认上述设置的边界，其他系统配置另行审查。

### 41. 安装成功但登记失败时保留资源

- 安装已成功且验证通过时，即使登记写入失败，也保留资源，不自动卸载或重新安装。
- 向 Agent 明确返回“安装成功、登记未完成”及实际路径，由 Agent 告知用户，不将整个流程报告为全部完成。
- 登记恢复可写后，核实资源现状并补登记；如已被扫描或其他操作登记，则更新同一条记录，避免重复。
- 待补登记信息仅在 .airoot 内保存；无法保存时如实报告，不另找目录写入，也不承诺重启后必定自动补齐。
- 登记修复前，资源已验证可用、既定权限要求满足且使用保护仍有效时，允许当前任务通过实际路径先使用，仍明确标示登记未完成。
- 如果登记故障同时导致使用中的资源无法受到保护，则暂停依赖该资源的步骤并说明原因。
- 不把尚未登记的资源当作正常登记资源向其他任务推荐；具体恢复触发方式另行确认。

### 42. 重启电脑必须单独确认

- 安装要求重启电脑时，AIRoot 标为高风险并返回原因与已知影响，由 Agent 单独取得用户对重启的明确同意，Full Access 同样适用。
- 能延后重启时记录待重启、待验证状态，先继续不依赖该资源的工作；重启后重新验证，通过后才标为可用。
- 安装前已知安装器无法禁止自动重启时，应在运行安装器前取得重启同意；普通安装授权不自动包含重启授权。
- 本条不承诺重启后 Agent 任务能够自动恢复。

### 43. 遵循项目依赖要求，调整需在授权范围内

- 由 Agent 识别项目已有依赖要求，AIRoot 按传入的明确要求准备环境，记录实际安装结果。
- 指定版本无法安装时，不擅自换版本或改写项目依赖文件；按既定有限重试规则仍无法满足，则说明障碍和调整方案，由 Agent 在用户尚未授权调整时取得确认。
- Full Access 本身不视为改变项目依赖要求的授权。用户已经明确要求升级或修复依赖时，在该授权范围内处理，无需重复确认。
- 项目未限定的版本可由 Agent 在兼容范围内选择，无需逐个询问。

### 44. 信息备份保存在 .airoot 内并有限轮换

- AIRoot 自动保留近期有效的信息备份，覆盖登记表、项目关联、用户备注、忽略记录和配置，全部存放在 .airoot 内。
- 备份仅包含信息，不复制环境、工具本体或项目文件。
- 按保留上限自动轮换过旧的自身备份，具体份数和空间上限另定；不得因写入失败或已知数据损坏覆盖最后的有效备份。
- 备份失败时如实说明，不擅自转存到其他目录。
- 登记表损坏时的自动恢复规则见第 45 条；恢复出的路径、可用性与占用情况需要重新核实，不能仅凭旧备份认定资源当前可用或空闲。具体恢复入口待定。

### 45. 登记表确认损坏时可自动恢复并告知

- 确认登记表损坏后，能先在 .airoot 内保留损坏原件，且不会覆盖正在进行的登记写入时，可自动从最近一份通过校验的备份恢复，无需每次另问。
- 向 Agent 返回所用备份时间及可能缺少的近期变更，由 Agent 告知用户。
- 恢复仅修复登记信息，不触发资源安装、升级、删除或旧操作重放；使用前重新核实资源实际状态，维护前重新核实占用，不以旧备份解除当前使用保护。
- 忽略记录或用户意图因近期数据缺失而不明时，不擅自重新纳管。
- 权限不足、临时占用或目录不可写不等于数据损坏，不因此执行回退。没有有效备份、无法保留原件或无法避免覆盖新写入时，保留现状并报告问题。
- 本条为产品规则，具体恢复实现与效果待验证。

### 46. 扫描发现不可用资源时先记录，按需修复

- 扫描与核查发现环境或工具异常时，记录已确认的问题，标明暂不可用或待验证，并集中告知；未能验证不直接认定损坏。

- AIRoot 向 Agent 返回准确结果，正常成功时由 Agent 简短说明做了什么、资源名称和版本、实际位置、关联项目及登记是否完成，可合并到当前任务的进度或完成说明。

## 四、十个场景，用来检验理解是否偏移

以下是场景示例，不代表已经扫描过用户的电脑，也不表示所有执行细节已经确认。

1. **首次安装**：找到已有 conda 环境、venv、ffmpeg、Git、Blender 等，分别登记。
2. **绘图任务**：找到已有合适环境，Agent 使用它完成绘图，而不是直接新建一套。
3. **视频任务**：返回已有 ffmpeg 的准确调用路径，不因 PATH 没配置而重复安装。
4. **新项目需要 conda**：创建指定 Python 版本的环境，验证后登记。
5. **新项目需要 venv**：在用户现有或指定的环境维护位置创建 venv，以任务简称命名并登记项目归属；不默认改成项目目录。
6. **缺少独立工具**：通过扳手安装工具，验证、登记，然后继续任务。
7. **工具装在环境内**：例如在某个环境安装 yt-dlp，登记它与环境的关系。
8. **漏扫便携工具**：用户指出 Blender 的位置，检查后补登记，不重装、不移动原文件。
9. **删除环境**：用户确认具体对象及已知影响后执行，核实删除成功再移除登记，并处理关联工具记录；使用中保护仍适用。
10. **删除工具**：确认具体实例后卸载，核实结果再移除登记，不删除项目成果文件；另支持只取消登记并保留文件。

## 六、逐轮审查记录

### 第一轮：升级能改动到什么程度？

**情境：**电脑里有一个已经能运行旧项目的环境。新任务需要升级其中的依赖，但升级可能导致旧项目不能运行。用户此时开启了 Full Access。

**反问：**你希望 AIRoot 在这种情况下怎么处理？

这一问不是重新要求安装授权，而是明确“直接安装或升级”的权限是否包含对既有工作成果承担兼容性风险。

**用户答复：**“新建环境，并以新任务简称命名，登记表里记录对应项目”

**当前结论：**有兼容性冲突时保留旧环境，新建以新任务简称命名的环境，并登记对应项目。Full Access 下直接执行。

### 第二轮：Full Access 是否允许 Agent 主动删除旧环境？

**情境：**Agent 已为新任务创建好环境，发现一个旧环境很久没用、占用空间较大。用户没有要求清理，当前开启 Full Access。

**反问：**你是否允许 Agent 自行删除这个旧环境并移除登记？

本轮确认“Full Access”是否同时授予主动清理的决策权；用户明确要求删除时的流程，以及失败安装产生的临时资源如何清理，另行讨论。

**用户答复：**“清理不允许，但是会在当前任务完成后提示用户”

**当前结论：**即使 Full Access 也不自行清理旧环境；发现清理候选时，在当前任务完成后提示用户，等待用户提出后续要求。

### 第三轮：用户笼统要求清理时，谁确定删除对象？

**情境：**任务结束后，Agent 提示存在可能闲置的旧环境。用户回复“帮我清理一下不用的环境”，但没有指定名称，当前开启 Full Access。

**反问：**这句话是否足以让 Agent 自己判断哪些环境不用了并直接删除？

本轮区分“用户允许开展清理”与“用户明确指定删除对象”；已确认笼统要求清理后，应列出环境及对应项目，由用户选定删除对象。

**用户答复：**“会主动列一下这几个环境和对应项目，然后确认删除哪个或哪些”

**当前结论：**用户笼统要求清理时，Agent 先列出候选环境及对应项目，由用户确认删除一个或多个环境，再执行删除并更新对应登记。Full Access 下同样遵守此流程。

### 第四轮：普通模式的一次安装授权覆盖多大范围？

**情境：**未开启 Full Access。Agent 做视频处理任务，先请求安装 ffmpeg，用户同意；任务继续后又发现需要安装一个 Python 依赖。

**反问：**第一次同意安装 ffmpeg，是否也授权了这个任务后续需要的其他安装？

### 扫描提速调研：GitHub 上可借鉴的方向（历史建议，必装载决定见第十七轮）

本轮只研究减少首次发现耗时的方向，没有对本机执行扫描，也没有安装任何组件。

1. **先查环境管理器和常见位置。** Microsoft 的 Python Environment Tool（PET，GitHub 项目 microsoft/python-environment-tools） 用于发现 Python 安装和虚拟环境，覆盖 Conda、venv、pyenv、Pipenv 等。项目说明它通过减少重复磁盘读取与额外启动进程来提高效率。它可作 Python 发现的参考，但不覆盖 AIRoot 的全部工具和非 Python 环境。
2. **Windows 可选用现成文件名索引。** Everything 的命令行工具 ES（GitHub 项目 voidtools/ES） 可以查询 Everything 已建立的索引。ES 需要 Everything 已安装并运行。官方示例中的初始文件名索引耗时随文件数量变化，普通文件夹索引比原生 NTFS 索引慢；这些数据不代表 AIRoot 完整登记耗时，本次未在用户电脑上实测。索引 NTFS 卷需要 Everything 服务或管理员方式，因此适合作为可选加速器，而不是 AIRoot 的硬性依赖。
3. **没有索引时再用快速遍历。** fd（GitHub 项目 sharkdp/fd） 使用并行目录遍历，但仍要遍历目录，实际收益需实测；默认会忽略隐藏文件和忽略规则，完整补扫时要特别设置。因此它适合后备扫描，不是避免全盘遍历的根本办法。

**建议流程（尚未确认）：**先从环境管理器和常见安装位置收集清单；再用可用的文件索引找环境标记和工具候选路径；只验证候选资源并登记；没有可用索引时，才对相应本机磁盘做后台补扫。首次结果保存后，日常优先核对登记与相关变化，避免每次重新扫全盘。

**反问：**你是否接受登记没补好时，只要资源已验证可用且使用保护仍有效，当前任务就可以先用；保护无法保证时再暂停相关步骤？

**用户答复：**可以。

**当前结论：**资源已验证可用，且既定权限要求与使用保护仍能满足时，当前任务可以通过实际路径先使用，仍明确说明登记未完成，之后核实补登记。如果无法保证使用保护，则暂停依赖该资源的步骤并告知原因。

### 第七十轮：安装要求重启电脑时怎么办？

**情境：**任务途中安装环境或工具，安装过程提示必须重启电脑才能完成或生效，但电脑上可能还有其他工作。

**建议：**AIRoot 将重启电脑标记为高风险，向 Agent 返回重启原因及已知影响，由 Agent 单独取得用户对重启的明确同意，Full Access 同样适用。能够延后重启时，记录待重启、待验证状态，先继续不依赖该资源的工作；重启后重新验证，通过后才标为可用。如果安装前已知安装器无法禁止自动重启，应在运行安装器前取得重启同意。普通安装授权不自动包含重启授权。本轮不承诺重启后 Agent 任务能自动恢复。

**反问：**你是否接受即使开启 Full Access，也必须由 Agent 单独征得你同意才能重启电脑；暂不重启时，先继续不受影响的工作？

**当前结论：**重启电脑标记为高风险，由 Agent 单独征得用户明确同意，Full Access 同样适用。暂不重启时记录待重启、待验证状态，继续不受影响的工作，重启后验证再更新可用状态。已知安装器会强制重启时，在运行前取得同意；不承诺任务自动恢复。

### 第七十一轮：项目指定的依赖版本安装不上时怎么办？

**情境：**给一个已有项目准备新环境，项目已经列出依赖及版本，但某个指定版本安装失败；换成其他版本可能装上，却未必符合项目原要求。

**建议：**由 Agent 先识别项目已有依赖要求，AIRoot 按传入的明确要求准备环境并记录实际安装结果，不擅自替换指定版本或改写项目依赖文件。按既定有限重试规则仍无法满足时，说明具体障碍及可选调整；若用户尚未授权调整依赖，由 Agent 确认是否允许变更，Full Access 本身不视为变更项目要求的授权。项目未限定的版本可由 Agent 在兼容范围内选择，不要求逐个询问。用户已明确要求升级或修复依赖时，在该授权范围内执行，无需重复确认。

**反问：**你是否接受优先遵循项目已有依赖要求，指定版本装不上时先说明并确认是否允许调整，而不为了安装成功自行换版本或改项目要求？

**用户答复：**可以。

**当前结论：**优先遵循项目已有依赖要求，指定版本无法安装时说明障碍与调整方案，尚未获准调整则由 Agent 确认后再变更。Full Access 本身不授权改变项目要求；项目未限定的版本可选择兼容版本，用户已授权升级或修复依赖时在该范围内直接处理。

### 第七十二轮：是否自动保留 AIRoot 信息的本地备份？

**情境：**登记表意外损坏，重新扫描虽能找回资源位置，但项目关联、用户备注、忽略记录等信息未必能靠扫描还原。

**建议：**AIRoot 在自身信息更新时自动保留有限数量的近期有效备份，全部放在 .airoot 内，覆盖登记表、项目关联、备注、忽略记录及配置；不复制环境、工具本体或项目文件。按保留上限轮换过旧的自身备份，具体份数及空间上限另定；不得因一次写入失败或已知数据损坏而覆盖最后的有效备份。备份失败时如实说明，不转存到其他目录。恢复入口和是否自动恢复另行确认；恢复出的路径、可用性及占用情况需要重新核实，旧备份不能作为资源当前可用或空闲的依据。

**反问：**你是否接受 AIRoot 自动在 .airoot 内保留有限数量的信息备份，并按上限轮换旧备份，用于找回项目关联和备注等内容？

**用户答复：**可以。

**当前结论：**AIRoot 自动在 .airoot 内保留有限数量的近期有效信息备份，包含登记、项目关联、备注、忽略记录与配置，按上限轮换过旧备份；不复制环境、工具本体或项目文件。具体保留份数与空间上限待定，自动恢复规则另行确认。

### 第七十三轮：登记表损坏时能否自动从备份恢复？

**情境：**AIRoot 确认登记表损坏，已无法正常读取，但 .airoot 内仍有通过校验的备份。

**建议：**在能先于 .airoot 内保留损坏原件、且不会覆盖正在进行的登记写入时，允许自动从最近一份通过校验的备份恢复登记信息，无需每次另问。告知 Agent 恢复所用备份的时间及可能缺少的近期变更。恢复只修复登记信息，不安装、升级、删除资源，也不重放旧操作；使用资源前重新核实路径、版本和可用性，修改或删除前重新核实占用，不以旧备份解除当前使用保护。忽略记录或用户意图因近期数据缺失而不明时，不擅自重新纳管。仅权限不足、临时占用或目录不可写时，不当作数据损坏执行回退；没有有效备份、无法保留原件或不能保证恢复不覆盖新写入时，保留现状并报告问题。具体恢复实现待验证。

**反问：**你是否接受登记表确认损坏时，AIRoot 保留原件后自动用最近的有效备份恢复，并告知恢复时间和可能遗漏的信息，资源使用前再核实实际状态？

**用户答复：**可以。

**当前结论：**登记表确认损坏时，在能保留原件且不覆盖新写入的条件下，自动从最近有效备份恢复并告知时间和可能遗漏的信息。恢复仅针对登记信息，不重放维护操作，资源使用前重新核实状态，不解除当前使用保护。无法可靠恢复时保留现状并报告。

### 第七十四轮：扫描发现不可用资源时是否主动修复？

**情境：**首次扫描或后续核查发现一个旧环境缺少依赖，或者某个工具不能正常调用，但当前任务不需要它。

**建议：**扫描与核查只记录已确认的问题，标明暂不可用或待验证，并集中告知，不因发现异常就主动补装、升级、重装或删除。只有当前任务确实需要，或用户明确要求修复时，才由 Agent 按既定权限、兼容性及使用保护规则安排处理；Full Access 不自动扩大为修复全机资源。未能验证不直接认定资源损坏。此规则不改变已确认的登记信息修复、外部变化同步，以及本次维护失败后的有限重试、回退和残留清理。

**反问：**你是否接受扫描发现暂不可用的环境或工具时先登记并提示，等任务需要或你明确要求时再修复，而不自动修复整台电脑？

**用户答复：**可以。

**当前结论：**扫描发现暂不可用的环境或工具时，先记录问题与状态并集中提示；任务需要或用户明确要求时再按既定规则修复。Full Access 不扩大为主动修复全机资源，未验证不直接等于损坏；既有登记修复与维护失败处理规则继续适用。
